== why twice, against the SAME database ==
The second run is the point of the file. Round 7 found that the live half
passed once per scratch database and never again: the SCHEMA block dropped
`players` without CASCADE, which succeeds on a virgin database and raises
DependentObjectsStillExistError on every run after it, so a block of tests was
red on the second run before a single assertion of their own had executed.
Nothing in the diff showed it. Running it twice is what showed it. A suite that
can only be green once is green for a reason that has nothing to do with the
code under test.

== the selection is part of the evidence ==
The expression is printed by the instrument immediately above each run, and it
is in the verbatim block below rather than quoted twice here. Two summary lines
with no record of the set that produced them are two numbers nobody can check;
a different selection prints the same shape. Round 10 prints the invocation
again beside EACH of the two runs, not only once in the header, because the
check this directory now enforces reads upward from a result line and requires
the command to be the nearest substantive line above it.

This round's two new live tests are inside the selection without the expression
changing, because they are named for what they are:

  test_pg_an_exhausted_progress_read_answers_503_with_no_progress_fields
      METHOD CHANGE 2, run. Both arms on which the post-capture re-read cannot
      be completed are driven for real -- a lobby identifier no read can
      resolve, so both relock attempts fail; and a lobby whose rows have been
      deleted, so the read succeeds and finds nothing. Both must answer 503
      with an EMPTY progress dict, with different reasons, and the refusal
      handler's body must be exactly the detail key.

  test_pg_a_seat_that_missed_an_update_recovers_in_one_submission
      METHOD CHANGE 1, run. A seat holding an advertisement watches another
      elector settle the parked game at that number, delivers the same body
      and is ECHOED with the next number on the echo, then keys a different
      physical game at the latched number and is refused terminally with both
      numbers on the refusal -- and the body derived from that refusal takes a
      number this endpoint accepts. One refused submission, no exclusion, one
      row per physical game at distinct numbers.

== the two lines this instrument rewrites, and why it does it HERE ==
pytest's own header names the interpreter and the rootdir by ABSOLUTE path,
which is this seat's checkout, and this report is committed. Round 7 removed
those two lines from its transcript after the fact; a log edited to be true is
not the same artifact as a log that was true when it was written. So the
substitution happens in the instrument, on exactly the two line shapes that
carry a path, anchored at the start of the line and keeping everything else the
line says. A filter that quietly ate a result line would show up as a missing
result rather than as a clean run.

== what a clean pair of runs means here ==
The two summary lines below are the whole verdict: the same selection, the same
database, run twice, with identical tallies.

  run one   52 passed, 103 deselected
  run two   52 passed, 103 deselected

Identical is the result this file exists to show. A second run that dropped
tests, or that passed fewer, would be the round-7 defect back: a live half that
is green once per virgin database and never again. Neither line carries a
`failed` term, and pytest prints one whenever a run has any, so its absence
from a line quoted verbatim IS the zero.

Both figures on both lines are the assembler's subject: each is a count next to
a term the run reports in, and each must appear in the log below as the same
integer beside the same term or this file does not get written.
