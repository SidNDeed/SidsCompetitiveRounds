== why twice, against the SAME database ==
The second run is the point of the file. An earlier round found that the live
half passed once per scratch database and never again: the SCHEMA block dropped
`players` without CASCADE, which succeeds on a virgin database and raises
DependentObjectsStillExistError on every run after it, so a block of tests was
red on the second run before a single assertion of their own had executed.
Nothing in the diff showed it. Running it twice is what showed it. A suite that
can only be green once is green for a reason that has nothing to do with the
code under test.

It is not an old worry this round could skip either, because this round ADDS a
live walk against that fixture and rewrites another. The new one settles a game
behind the endpoint, drives a conflicting account of it through the endpoint,
and then reads back both the match rows and the quarantine table -- more rows
written, and one more table read, per run against the same database. A fixture
that grows is exactly the shape the defect above lives in, and the second run
below is what says it did not come back.

== the selection is part of the evidence ==
The expression is printed by the instrument immediately above each run, and it
is in the verbatim block below rather than quoted twice here. Two summary lines
with no record of the set that produced them are two numbers nobody can check;
a different selection prints the same shape. The invocation is printed again
beside EACH of the two runs, not only once in the header, because the check
this directory enforces reads upward from a result line and requires the
command to be the nearest substantive line above it.

== this round's new test is in the selection, and the expression did not move ==
`test_pg_a_conflicting_account_of_the_settled_game_is_dropped_and_kept` is the
witness the lens asked for: a differing account of the physical game another
elector has already settled, refused with the same answer a later game gets,
dropped, and kept on the quarantine record -- with the lobby's rows read over
the WHOLE lobby rather than at the settled number, because a redirect puts its
second row at the free one. It is PostgreSQL-gated and its name begins
`test_pg_`, so the first clause of the expression already selects it and no
clause was added. The rewritten missed-update walk is likewise a rewrite in
place of a test the same clause carries.

== the two lines this instrument rewrites, and why it does it HERE ==
pytest's own header names the interpreter and the rootdir by ABSOLUTE path,
which is this seat's checkout, and this report is committed. A log edited to be
true after the fact is not the same artifact as a log that was true when it was
written, so the substitution happens in the instrument, on exactly the two line
shapes that carry a path, anchored at the start of the line and keeping
everything else the line says. A filter that quietly ate a result line would
show up as a missing result rather than as a clean run.
