The PostgreSQL-gated selection, run TWICE against ONE database, 2026-09-21 (round 9)
====================================================================================

Instrument: backend/tests/evidence/run-pg-controls.sh, committed beside this
report and taking its DSN from the environment.

== why twice, against the SAME database ==
The second run is the point of the file. Round 7 found that the live half
passed once per scratch database and never again: the SCHEMA block dropped
`players` without CASCADE, which succeeds on a virgin database and raises
DependentObjectsStillExistError on every run after it, so fourteen tests were
red on the second run before a single assertion of their own had executed.
Nothing in the diff showed it. Running it twice is what showed it. A suite that
can only be green once is green for a reason that has nothing to do with the
code under test.

== the selection is part of the evidence ==
The expression is printed by the instrument immediately above the runs, and it
is in the verbatim block below rather than quoted twice here. Two summary lines
with no record of the set that produced them are two numbers nobody can check;
a different selection prints the same shape.

This round's two new live tests are inside it without the expression changing,
because they are named for what they are:

  test_pg_a_realigned_sitting_issues_each_game_its_own_number
      Finding 1, run. It drives a lobby past the advertised number and states
      the three facts the corrected rule rests on: the parked game settles at
      `E`, the next physical game settles at `E + 1`, and a SECOND physical
      game keyed at `E` is refused with `E` named as settled. The lobby ends
      holding one row per physical game at distinct numbers.

  test_pg_a_catch_up_on_a_refusing_path_logs_a_claim_its_transaction_can_keep
      Finding 5, run. The counter catch-up is exercised on a path that never
      commits, and the lobby row is read back AFTER the refusal is answered and
      required to be exactly where it started -- so the log line's wording and
      the row it describes are asserted together and cannot drift apart.

== the two lines this instrument rewrites, and why it does it HERE ==
pytest's own header names the interpreter and the rootdir by ABSOLUTE path,
which is this seat's checkout, and this report is committed. Round 7 removed
those two lines from its transcript after the fact; a log edited to be true is
not the same artifact as a log that was true when it was written. So the
substitution happens in the instrument, on exactly the two line shapes that
carry a path, anchored at the start of the line and keeping everything else the
line says. A filter that quietly ate a result line would show up as a missing
result rather than as a clean run (#441).

== what a clean pair of runs means ==
Identical counts in run 1 and run 2 is the positive signal: the selection is
idempotent against a database that already holds its tables, so the next round
can re-run it without provisioning anything.

The selection resolves to FORTY-NINE tests, which is round 8's forty-seven plus
this round's two. Both of those are live-gated, and each appears as a PASSED
line TWICE below, once per run -- stated because a test that is in the file but
outside the selection expression contributes nothing, and the way to tell the
two apart is to read its own result line rather than the total. The
twenty-seven live checks the suite pair's two halves differ by are inside this
forty-nine, together with twenty-two that need no server -- the opt-out guard
cases and the source-reading checks -- which run in the same selection on
purpose, since they are what stops the other twenty-seven turning into silent
skips.
