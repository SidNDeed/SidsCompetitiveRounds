== why twice, against the SAME database ==
The second run is the point of the file. An earlier round found that the live
half passed once per scratch database and never again: the SCHEMA block dropped
`players` without CASCADE, which succeeds on a virgin database and raises
DependentObjectsStillExistError on every run after it, so a block of tests was
red on the second run before a single assertion of their own had executed.
Nothing in the diff showed it. Running it twice is what showed it. A suite that
can only be green once is green for a reason that has nothing to do with the
code under test.

This round has its own reason to run it twice. Its two new walks install a
TRIGGER, a trigger function and a SEQUENCE -- the one-shot fault that fails an
entry's INSERT at N exactly once -- and remove all three in their own
`finally`, and the helper that installs them drops any of the three before it
creates them. The one-shot count lives in the sequence because a sequence is
the one counter a rollback does not undo, which also makes it exactly the kind
of object a fixture that drops and recreates its tables does not reset. Each
walk asserts the fault's effect -- a retryable answer carrying the lobby's
progress -- so a fault that did not fire, or fired twice, reds rather than
passes; the second run below is what says a second pass over the same
database meets the same fault.

== the selection is part of the evidence ==
The expression is printed by the instrument immediately above each run, and it
is in the verbatim block below rather than quoted twice here. Two summary lines
with no record of the set that produced them are two numbers nobody can check;
a different selection prints the same shape. The invocation is printed again
beside EACH of the two runs, not only once in the header, because the check
this directory enforces reads upward from a result line and requires the
command to be the nearest substantive line above it.

== this round's new tests are in the selection, and the expression did not move ==
`test_pg_a_retried_entry_meets_the_settlement_made_while_it_waited` is the
witness the round-10 lens asked for on the retryable arm: an entry keyed at N,
its INSERT failed once, a second elector's differing account settled at N in
the window the rollback opens, the 503 advertising N+1, and the retry going out
as the same body at N -- answered `settled_game`, dropped, its payload on the
quarantine record, and no second row at ANY number of the lobby.
`test_pg_a_retried_entry_settles_its_own_number_when_nothing_settled_it` is its
other half: the same fault with nothing settled meanwhile, the retry accepted
at N. Both are PostgreSQL-gated and both names begin `test_pg_`, so the first
clause of the expression already selects them and no clause was added.

== the two lines this instrument rewrites, and why it does it HERE ==
pytest's own header names the interpreter and the rootdir by ABSOLUTE path,
which is this seat's checkout, and this report is committed. A log edited to be
true after the fact is not the same artifact as a log that was true when it was
written, so the substitution happens in the instrument, on exactly the two line
shapes that carry a path, anchored at the start of the line and keeping
everything else the line says. A filter that quietly ate a result line would
show up as a missing result rather than as a clean run.

== what a clean pair of runs means here ==
The two summary lines below are the whole verdict: the same selection, the same
database, run twice, with identical tallies.

Identical is the result this file exists to show. A second run that dropped

term, and pytest prints one whenever a run has any, so its absence from a line
quoted verbatim IS the zero.

Both figures on both lines are the assembler's subject: each is a count next to
