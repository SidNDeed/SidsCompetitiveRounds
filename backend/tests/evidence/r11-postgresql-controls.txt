== why twice, against the SAME database ==
The second run is the point of the file. Round 7 found that the live half
passed once per scratch database and never again: the SCHEMA block dropped
`players` without CASCADE, which succeeds on a virgin database and raises
DependentObjectsStillExistError on every run after it, so a block of tests was
red on the second run before a single assertion of their own had executed.
Nothing in the diff showed it. Running it twice is what showed it. A suite that
can only be green once is green for a reason that has nothing to do with the
code under test.

== the selection is part of the evidence ==
The expression is printed by the instrument immediately above each run, and it
is in the verbatim block below rather than quoted twice here. Two summary lines
with no record of the set that produced them are two numbers nobody can check;
a different selection prints the same shape. The invocation is printed again
beside EACH of the two runs, not only once in the header, because the check
this directory enforces reads upward from a result line and requires the
command to be the nearest substantive line above it.

== this round's three new tests are in the selection, and the expression says so ==
None of the three is PostgreSQL-gated: they are closing checks over this
directory's own evidence, and they run identically with and without a DSN. The
selection carries them anyway, for the reason it already carries the other
evidence-level checks -- this run is where the closing set is exercised as a
set, twice, so a check that only holds on a virgin database would show up here
rather than in a reviewer's hands. Three clauses were added to the expression
and are visible in it below:

  test_the_assembler_counts_the_checks_it_ran
      The assembler's self-test count, compared with the records its run
      produced AND with a traced count of the invocations that run made. The
      constant it used to print was one short of what the body ran, on the one
      instrument here whose purpose is to refuse a number a run did not
      produce.

  test_the_new_controls_a_report_claims_are_the_ones_the_inventory_tags
      A mutation-controls report's list of what is new in its round, compared
      with the module inventory's round tags in both directions. It also
      requires the newest round's report to carry the list at all -- a round
      may not answer the rule by making no claim -- and asks the same question
      keyed on CONTENT, so a report of the newest round that names the mutation
      runner's log as its stdout is bound whatever it is called.

  test_the_residual_reach_rule_holds_in_both_directions
      The residual list's reach rule, proved on its own fixtures: a list as
      stated is clean, a second statement of the reach in prose is refused, an
      untagged item is refused, a tally disagreeing with its tags is refused,
      and a reword beside a tag leaves the rule quiet.

A fourth of this round's changes needed no new clause, and saying so is part of
the record rather than an omission: the sixth control mutates the invocation
rule's list of frame keys, and the check it reds is
`test_the_committed_evidence_re_derives_its_own_numbers`, which the expression
already carries under `committed_evidence`. A round that added a clause for
every change regardless would make the selection a list nobody could read
against the tests it names.

== the two lines this instrument rewrites, and why it does it HERE ==
pytest's own header names the interpreter and the rootdir by ABSOLUTE path,
which is this seat's checkout, and this report is committed. Round 7 removed
those two lines from its transcript after the fact; a log edited to be true is
not the same artifact as a log that was true when it was written. So the
substitution happens in the instrument, on exactly the two line shapes that
carry a path, anchored at the start of the line and keeping everything else the
line says. A filter that quietly ate a result line would show up as a missing
result rather than as a clean run.

== what a clean pair of runs means here ==
The two summary lines below are the whole verdict: the same selection, the same
database, run twice, with identical tallies.

  run one   55 passed, 103 deselected
  run two   55 passed, 103 deselected

Identical is the result this file exists to show. A second run that dropped
tests, or that passed fewer, would be the round-7 defect back: a live half that
is green once per virgin database and never again. Neither line carries a
`failed` term, and pytest prints one whenever a run has any, so its absence
from a line quoted verbatim IS the zero.

Both figures on both lines are the assembler's subject: each is a count next to
a term the run reports in, and each must appear in the log below as the same
integer beside the same term or this file does not get written.
