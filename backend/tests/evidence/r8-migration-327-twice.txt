Migration 327 applied TWICE through `psql -f`, 2026-09-20 (round 8)
===================================================================

The way the deploy applies it: `psql -f`, not asyncpg's simple-query path,
because the file carries its own BEGIN/COMMIT and `psql -f` does not wrap a
file in a transaction (#340). Run against local PostgreSQL 16.9 on this seat.

Instrument: backend/tests/evidence/migration-327-twice.sh, against the table in
backend/tests/evidence/migration-327-fixture.sql. Both are committed beside
this report and take their connection from the environment.

== what round 8 changed about this file, and why ==

ROUND 7 CARRIED A USAGE TEMPLATE WHERE ITS INVOCATION BELONGS. The header said
how the script COULD be called; it did not say how it WAS. Those are different
claims, and only one of them is evidence: a template is satisfied by any run,
including one against another database or another migration file. The script
now prints the command, the interpreter, both file paths and the database
immediately above the runs, and that block is the first thing below this note.

THE PATHS ARE REPOSITORY-RELATIVE BECAUSE THE SCRIPT MAKES THEM SO. psql echoes
whatever path it was handed in every NOTICE it raises, so the absolute paths
round 7 passed put this seat's checkout into the log, and round 7 removed them
from the transcript afterwards. Editing a log to make it true is the wrong end:
the script now cd's to the repository root and names both files relative to it,
so the line psql prints is already the line this file should carry. It reads
`psql:backend/tests/evidence/migration-327-fixture.sql:2` below, and nothing in
this file has been edited after the run.

== what the run proves, in order ==
  * the backfill numbers every row whose room tail is derivable, and leaves
    the `_r0` and `_r99999` rows NULL rather than inventing a number;
  * the post-check raises only for a row that WAS derivable and was left NULL;
  * the SECOND run changes no row -- the two dumps are diffed and the diff is
    empty -- so re-applying the migration is a no-op, not a second backfill;
  * NOT NULL and the 1..999 CHECK both hold afterwards;
  * a writer row keeps the number the inserting statement supplied;
  * an UNNUMBERED insert, which the old api still makes in the migration-first
    window, is numbered by the trigger from its room tail rather than refused.
