ROUND 7. Run TWICE against ONE scratch database, and the second run is the
point of the file.

Round 7's own live controls needed a second set of tables -- MONEY_SCHEMA:
players with gold_spent, gold_transactions, lobby_bets, bets, ranked_series --
and every one of those carries a foreign key to `players`. The older SCHEMA
block dropped `players` WITHOUT CASCADE, which succeeds on a virgin database
and raises DependentObjectsStillExistError on every run after the first. The
live half of the file therefore passed once per scratch database and never
again: 14 of these tests were red on the second run, before a single
assertion of their own had executed. Nothing in the diff showed it. Running it
twice is what showed it.

The drop is CASCADE now, in both schema blocks, and each block drops and
recreates its own tables before using them, so neither depends on constraints
the other left behind. The two summaries below are the same selection run
back-to-back against the SAME database -- the second is the one that could
not pass before.

Selection (the expression is part of the evidence; a set nobody can rebuild
is a count nobody can check):

  FFA_TEST_PG_DSN=postgresql+asyncpg://<user>@<host>:<port>/<db> \
  python -m pytest tests/test_ffa_game_number_anchor.py -v -p no:cacheprovider \
    -k "pg_ or opt_out or missing_dsn_alone or one_transaction or locked_slot
        or weakest_mode or wager_cannot_be_inserted or relock_leaves
        or committed_evidence or round_seven_control"

round 7's three), the 13 opt-out guard cases and the 7 source-reading checks.
