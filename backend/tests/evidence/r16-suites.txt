== THE CAPTURE IS WRITTEN OUTSIDE THE REPOSITORY ==
The evidence-log re-inclusion means a capture sitting in this directory is
UNTRACKED-AND-NOT-IGNORED, which is exactly the set the fence walks. A run
redirected straight into this directory would therefore fingerprint its own
growing log, compare it with itself and report MOVED. The capture is copied in
after the pair has finished.

== THIS REPORT IS ITS OWN RUN'S OUTPUT ==
The narrative above the marker is written; everything below it is the exact
bytes of the log named in the `stdout:` header. This file is ASSEMBLED by
backend/tests/evidence/assemble-evidence.py, which REFUSES to write it at all
when a number in the narrative is absent from that log. Two rules decide what
a number is -- a count next to a term a run reports in, and any integer of
three digits or more that is not one of the typed exempt shapes -- and the
assembler's self-test asserts both fire and both stay quiet, so a typo in
either pattern reds rather than passing for ever.

The invocation of each half is printed by the script immediately before it
runs, and is in the verbatim block below rather than quoted up here.

== THE FENCE, and the claim it is allowed to make ==
A suite that overlaps an edit to its own tree certifies nothing, and a sentence
saying it did not is a claim written from the one state its author had in mind.
So the tree is fingerprinted by backend/tests/evidence/tree-fingerprint.sh at
the start and again at the end, and the instrument RE-DERIVES its set at every
call: `git diff --name-only HEAD` for tracked files differing from HEAD, and
`git ls-files --others --exclude-standard` for files present but untracked. The
paths are part of the value, so an addition or a removal moves the fingerprint
even when every surviving file is untouched, and an unreadable path prints an
EMPTY hash rather than being skipped. The script refuses to run at all if the
fingerprint comes back empty.

THIS ROUND'S SET IS THE SMALLEST ONE THE ORDER ALLOWS. Everything the landing
changed in tracked files -- the thirty picks, the re-pin of the route manifest
and the negations that admit this round's captures -- was COMMITTED before the
controls ran, so no tracked file differs from HEAD. What the fence lists is
the 8 paths the controls produced before this pair: their captures and
the two reports assembled from them. Nothing the fence lists is written
afterwards. What is written afterwards is this report and the assembly record,
and neither can exist before the run it quotes -- which is why the directory is
checked again, as committed, by the re-pin wrapper that runs last of all.

Ignored paths stay out, by `--exclude-standard`, which is also why the
per-half pytest logs go outside the repository.

That guard is not an argument; it is run, with its negative control, in
r16-mutation-controls.txt: each edit class is PERFORMED and the guard is
required to notice, and no edit at all is required to leave it quiet.

== the route manifest was re-pinned BEFORE this pair, and the last re-pin
   still has to rewrite nothing ==
The lane's rounds re-pin last and expect no row to move, because a lane round
ships no handler change. The landing is different: every pick took main's side
of the manifest, so the fingerprints of the handlers the lane had changed were
main's until the manifest's own tool re-pinned them over the landed tree, once,
in its own commit, before any evidence ran. The route-manifest gate in both
halves below is therefore run against that re-pin. The wrapper that runs last
of all re-pins again and reports its rewritten-row count; after that commit no
handler moved, so the count has to be zero.

== what the numbers mean ==
The skip count in the opt-out summary IS a check, not a footnote: an opt-out
run that skipped as few as the live run did is a live run wearing the opt-out's
name. The two halves are two different questions, and `env -u` is what keeps
them that way.

== the difference between the halves, and it reconciles ==
The two summary lines are in the verbatim block below, each under the command
that produced it:

  opt-out   1882 passed, 38 skipped, 5 warnings in 735.22s (0:12:15)
  live DSN  1914 passed, 6 skipped, 5 warnings in 750.07s (0:12:30)

The live half runs the FFA-gated checks the opt-out half skips, so the
difference has to appear twice in the same two lines: the live half's surplus
of passes and the opt-out half's surplus of skips are the same set of checks.
Here the live half passes exactly as many more checks as the opt-out half
skips more, and neither line carries a failure. Two numbers from two
different columns of the same two lines agreeing is the check; a
disagreement there would be a finding, not a rounding error.

Those four figures are the assembler's subject, not decoration. Each is a count
next to a term the run reports in, so each must appear in the log below as the
same integer beside the same term or this file does not get written -- which is
what the mutation control `suites-report-carries-an-underived-number`
demonstrates by putting a figure here that no run can print.

== against r15-suites.txt, named rather than copied ==
The lane's last pair is r15-suites.txt, and the two pairs are not expected to
agree: the test sets differ in the three ways listed at the top, so these lines
are main's suite with the lane's tests in it, not the lane's lines plus a delta.
No previous round's figure is quoted here, deliberately. Every number in this
narrative has to appear in the log below it or the assembler refuses to write
the file, and a number from a DIFFERENT run cannot.

== failures in either run ==
Neither summary line above carries a `failed` term. pytest prints one whenever
a run has any, so its absence from a line quoted verbatim IS the zero, and it
is re-derivable from this file alone. Both halves also returned rc=0, printed
immediately above the line they describe.

Neither summary line carries an xfailed count this round, where each of the
lane's lines carried one. The test that was marked expected-to-fail pins a
version floor that a batch in the stack beneath the lane introduced; that batch
is not on main, main's copy of the file does not carry the test, so it did not
run here -- which is neither a pass nor a failure. The gate used for these
reports tests the TERM rather than the substring, and carries that shape and
its negative twin as assertions that run every time it is imported.
