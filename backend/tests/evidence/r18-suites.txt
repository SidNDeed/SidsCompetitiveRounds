== THE FENCE, and what it holds this round ==
A suite that overlaps an edit to its own tree certifies nothing. So the tree
is fingerprinted by backend/tests/evidence/tree-fingerprint.sh at the start
and again at the end; the instrument re-derives its set at every call --
tracked files differing from HEAD, and files present but untracked -- and the
paths are part of the value, so an addition or a removal moves it even when
every surviving file is untouched. The script refuses to run at all when the
fingerprint comes back empty.

Every tracked change of this round -- the runner's swap rule and its tests,
the inventory entry, the attributes file, and the negations that admit this
round's captures -- was COMMITTED before the pair, so no tracked file differs
from HEAD. What the fence lists is the one path this round produced before
the pair: the capture of the committed mutation runner's single run at this
tip, r18-mutation-run.log. Unlike round 17's run, this one passed the gate
that stopped that one: it took its swap from the newest report that lists a
new control, resolved every anchor exactly once, and ran its whole campaign
-- every control red under its mutation and green under its inert edit, and
every file it mutated restored byte for byte -- in its own words on its first
and last lines. It is committed with this report, unchanged.

Ignored paths stay out, by `--exclude-standard`, which is also why the
per-half pytest logs go outside the repository.

== what the numbers mean ==
The skip count in the opt-out summary IS a check, not a footnote: an opt-out
run that skipped as few as the live run did is a live run wearing the opt-out's
name. The two halves are two different questions, and `env -u` is what keeps
them that way.

The live half runs the FFA-gated checks the opt-out half skips, so the

different columns of the same two lines agreeing is the check; a
disagreement there would be a finding, not a rounding error.

Those four figures are the assembler's subject, not decoration. Each is a count
next to a term the run reports in, so each must appear in the log below as the
